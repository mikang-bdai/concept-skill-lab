# 大模型的上下文

> 一句话总结：大模型每次"思考"时能看见的全部信息窗口，决定了它这一轮能记住什么、能用什么。

## 1. 一句话定义
上下文（Context）是**大模型在一次对话/一次推理中能看到的全部输入信息**——包括系统提示、用户消息、历史对话、工具返回结果，以及任何被塞进 prompt 窗口里的内容。

## 2. 解决什么问题
- **场景**：用户和大模型多轮对话，模型需要"记得"前面说过的话、给过的资料、之前的结果
- **痛点**：模型本身没有"长期记忆"（权重是训练完就冻住的），任何"上下文之外"的信息它都看不见
- **不解决的后果**：用户每次都要重贴背景，模型回答前后矛盾；多轮对话根本无法进行；连"我说啥你都得接住"这种基本体验都做不到

## 3. 核心要点（5-8 条）
- **上下文窗口**（Context Window）是模型硬性上限：所有输入+输出 token 数不能超过这个值，超了就报错或被截断
- 上下文包含：system prompt + 历史消息 + 当前用户输入 + 工具返回结果 + 模型生成内容（已生成部分会作为下一轮的输入）
- **不是长期记忆**：模型在两段独立的对话之间互不记得，每段对话有自己的上下文窗口
- 上下文长度单位是 **token**（不是字），中文一个字符约 1-2 token，英文一个词约 1-3 token
- **上下文衰减**：很多模型对窗口中段的信息"注意度"比首尾低（Lost in the Middle 现象），重要内容放头尾最稳
- **上下文窗口 = 模型的工作记忆**：决定它能"看到"什么、能引用什么、能在多大范围内推理
- 上下文管理（塞什么、删什么、压什么）是大模型应用开发的核心工程能力
- 当上下文超长时，需要**截断 / 摘要 / RAG** 等技术主动管理，不能盲目堆

## 4. 常见误解
- ❌ "上下文 = 训练数据" → ✅ 错。训练数据在模型参数里，权重一旦训练完就改不动；上下文是每次推理临时塞进去的输入
- ❌ "上下文越长模型越聪明" → ✅ 不一定。上下文窗口大 ≠ 都能用好；多数模型在窗口用满时性能会下降
- ❌ "上下文中提到的就是模型'知道'的" → ✅ 错。它能"看见"，但不一定"记住"或"会用"——尤其是窗口中后段
- ❌ "清空上下文后模型会保留印象" → ✅ 错。完全无记忆，新一段对话从零开始
- ❌ "上下文窗口单位是字数" → ✅ 错。单位是 token，需要看模型的 tokenizer

## 5. 跟其他概念的关系
- 跟 **Prompt**：Prompt 是"塞进上下文的内容之一"（通常是 system + user 部分），上下文是更宽的概念
- 跟 **RAG（检索增强）**：RAG 是为了"突破上下文窗口限制"——把超长的资料先检索出相关部分，再塞进上下文
- 跟 **Memory / 记忆系统**：Memory 是把"上一段对话的信息"持久化下来，下一段对话开始前再塞进上下文，是一种跨会话的状态管理
- 跟 **Token**：上下文长度按 token 计费，token 是计费和窗口的最小单位
- 跟 **Agent**：Agent 的"短期记忆"本质就是它的当前上下文，工具返回结果也会被追加到上下文里

## 6. 一个例子 / 类比
把大模型想象成一个**只能坐在一张小桌子前的学霸**：

- 桌面（上下文窗口）就是他能同时摊开看的所有材料
- 他没法起身去书架自己找资料（那叫 RAG，要别人帮他找好放桌上）
- 他看完桌上的材料才能回答问题，桌面外的他看不到
- 你跟他聊第三轮时，前两轮的聊天记录必须重新摆到桌面上，他才记得；你把材料撤走，他就忘了
- 桌面是有限的，材料多了要叠起来放，最下层的（中间段）他看得最糊
