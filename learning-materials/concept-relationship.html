Agent · 上下文 · Skill — 三者关系

概念关系 04   结构协作时序

三个概念不是孤立的——Agent 是舞台，上下文是工作记忆，Skill 是岗位手册。拆开各管一摊，合起来才能跑出能办事的 AI。

结构关系图

怎么读这张图：外层虚线框 = Agent 舞台，内部三个核心部件（LLM 大脑、上下文窗口、工具集）由 循环控制器 串起来。
关键洞察 1：Skill 不直接被 Agent 调用——它要先 注入到上下文窗口（通常以 system prompt 片段的形式），LLM 才能"看到"它、才会按它的规则办事。
关键洞察 2：工具的返回结果也会被回写到上下文——所以上下文窗口的大小，直接决定了 Agent 一次能"看到"多少工具结果、历史消息和 Skill 指令。

三方对比表

本质 工程实体：能办事的 AI 角色 运行时窗口：模型一次能"看见"的全部信息 结构化文档：可复用的指令包

谁来定义 开发者用代码 + LLM + 工具拼出来 由"塞了什么"决定：system / 用户 / 工具 / Skill 注入 人或团队写一次，可被多次复用
什么时候存在 运行时（跑起来才有） 运行时（每次推理都是新窗口） 静态文件 SKILL.md，需要时加载
解决的核心问题 让 AI 从"会说话"变成"会办事" 让 AI 在多轮交互中能"记得"+"能用"信息 让好的工作流可以沉淀、复用、跨会话一致
典型失败模式 规划走偏、工具调错、死循环 超长截断、中段衰减（Lost in the Middle） 规则太粗没用、太细难维护、相互重叠
一句话定位

Agent 负责"接目标、想办法、动手干"，上下文 负责"它这一轮能看见啥、记住啥"，Skill 负责"按什么规则 / 走什么流程 / 输出什么格式"。

三者不是替代关系，是层叠关系 —— 一个能稳定干活的 Agent，一定同时具备三者。

协作时序：Agent 跑一次任务发生了什么

把三个概念放进一个真实场景 —— "用户让 Agent 总结一个陌生概念"，看看每一步三者各扮演什么角色：

1
用户

说："learn-a-concept: 大模型的上下文"。

2
Agent 循环控制器

识别到调用意图 → 把 learn-a-concept 这个 Skill 的内容从 .workbuddy/skills/ 里读出来，注入到上下文窗口的 system prompt 部分。

3
LLM 大脑

看到 上下文：system 部分有 Skill 规则 + 9 章节模板，user 部分是"大模型的上下文"。开始按 Skill 模板规划怎么写。

4
LLM → 工具

决定调 search_web / Read 工具验证资料 → 结果回写到上下文（追加到对话历史）。

5
LLM 大脑

再次思考：上下文里有 Skill 规则 + 工具结果 → 决定继续写还是停。

6
Agent 循环控制器

判断输出完成 → 调 Write 工具把内容写到 notes/02-...md → 把"写入成功"也加进 上下文，返回给用户。

关键洞察（必须记住）

三者缺一不可

没有 Skill：Agent 也能跑，但每次输出格式 / 工作流不稳定，全靠 LLM 临场发挥。

没有上下文：Agent 不可能存在 —— LLM 每次推理都从零开始，连用户的指令都看不见。

没有 Agent：Skill 和 上下文 只是"原材料"，没人驱动就跑不出活儿。

Skill 一定要进上下文才生效

SKILL.md 文件躺在磁盘上，不会自动生效。必须是 Agent 循环控制器把它读出来、塞进上下文的 system prompt 段，LLM 才能"看到"它、才会按它办事。

这也意味着：如果 Skill 太长，会挤占上下文窗口，留给历史消息和工具结果的空间就变少了。

上下文是 Agent 的"短期记忆"

Agent 看起来有"记忆"，其实只是因为它的当前上下文窗口里有这些信息。清空上下文 = Agent 失忆。下一段对话开始，Skill 通常要重新注入，否则按默认行为跑。

三者不在一个层级

很多人会问"Agent 和 Skill 哪个重要"——其实问错了。它们是不同维度的：

  • Agent 是"谁在干活"（角色 / 实体）
  • 上下文 是"它知道什么"（信息 / 状态）
  • Skill 是"它按什么规矩干活"（规则 / 流程）
